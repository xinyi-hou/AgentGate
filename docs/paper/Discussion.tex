\section{讨论}
\label{sec:discussion}

\subsection{部署方式与扩展能力}
\label{subsec:deployment-extensibility}

AgentGate的部署位置由工具调用链路中的信任边界决定，而不依赖某一种特定的智能体框架。系统采用统一安全内核，并支持两种互补的接入方式。第一种方式是在智能体宿主进程内通过框架适配器接入，在工具注册、调用执行前和结果写回上下文前触发网关分析。这种方式能够获得用户任务、智能体状态与工具返回内容等较完整的上下文，适合Function Tool以及LangGraph、OpenAI Agents SDK等框架原生工具。第二种方式是将网关作为独立Sidecar部署在智能体宿主与工具服务之间，或者置于工具服务入口，对多个智能体发出的调用实施统一策略。该方式能够减少对智能体应用的侵入，并使资源身份、租户边界与后端实际效果更容易纳入强制控制。两种方式并非两套独立的防护系统，而是将工具声明、任务契约、调用参数、返回结果和会话标识转换为相同的内部表示，复用工具内容处理、任务级授权和调用轨迹控制三个模块。部署在不同位置时，系统仅需调整可观测证据与可执行动作；在组合部署场景下，还可通过会话标识和数据来源标记关联两侧状态，避免分别决策造成安全语义割裂。

这种设计将系统能力与具体协议解耦。接入新的智能体框架时，适配器只需将工具注册、调用前和返回后三类事件转换为网关对象，不需要修改核心分析逻辑；接入新的工具领域时，则可通过扩展资源目录、工具画像、效果推断器与策略约束描述领域特有的资源和副作用。语义分析器的职责被限制为抽取动作、资源、范围、效果、目的地及外部指令等受限事实，最终决策仍由任务授权上界、确定性约束和会话状态共同产生，因此可通过OpenAI兼容接口替换不同能力与成本的大语言模型，而无需改变策略执行流程。上述扩展路径使AgentGate能够在框架、工具类型和语义模型变化时保持一致的安全表示与判定接口。

当前原型已实现FastAPI Sidecar、Function Tool适配器以及LangGraph和OpenAI Agents SDK的轻量封装，可以验证进程内接入与独立服务接入两种基本形态。对于MCP，现有适配器能够将\texttt{list\_tools}结果转换为内部工具对象，并生成\texttt{tools/call}请求，但尚未覆盖客户端会话管理、远程连接、结果转发与异常重连，因而目前体现的是协议适配能力，而非完整的透明MCP代理。完成这些协议生命周期功能不会改变三个安全模块的输入输出关系，但仍是将原型扩展为通用工具网关所需的系统工作。

\subsection{局限性}
\label{subsec:limitations}

AgentGate已经通过结构化任务契约、参数绑定后的效果推断以及语义模型辅助分析缩小任务授权边界，但自然语言任务通常只描述最终目标，并不会穷举完成任务所需的全部辅助操作。若契约过于严格，身份核验、信息检索和格式转换等正常前置步骤可能被误判为范围扩张；若为兼容这些步骤而放宽契约，智能体又可能借助自行生成的子任务扩大权限。实验中的误报主要集中在动作约束不匹配、任务与调用语义不一致以及资源、范围和目的地约束过度收缩，三套轨迹基准中的501例误报有158例来自全正常交互，并导致112条正常交互提前终止。这说明当前方法虽以企业权限上界限制授权扩张，仍难以仅凭任务文本同时获得完整的流程知识与精确的最小权限，任务效用与安全边界之间仍存在难以消除的权衡。

系统通过指令--数据边界识别、来源标记和跨工具引用分析检测外部内容的操控意图，并要求高风险调用具有任务、效果和来源证据。然而，检测到外部指令并不等价于证明后续调用由该指令触发：工具结果可能同时包含正常业务数据和隐式重定向，智能体也可能在若干个正常推理步骤之后才执行受影响的操作。在ASB-Traj的245例漏报中，有118例已经识别出外部内容影响，但因调用在动作、资源与效果上仍与表面任务一致，且缺少外部指令与调用之间的充分因果证据而被放行。若将弱相关性直接视为因果关系会显著增加误报，而要求显式数据依赖又会遗漏语义改写、间接引用和延迟触发，因此，如何在不读取或约束智能体完整内部推理的前提下建立稳健的因果归因，仍是内容风险与调用授权协同中的主要限制。

对于跨调用风险，AgentGate已维护字段级敏感标签、动态执行图、累计风险预算和审批消费状态，能够处理直接的数据传递、分批读取、凭证使用与审批重放。但真实调用链中的数据可能经历摘要、翻译、编码、拆分和重新生成，工具服务还可能产生网关不可观测的内部副作用，使基于明文证据和已知工具效果的标签传播出现遗漏或过度污染。当前执行图主要用于保存依赖证据和辅助路径判断，尚未形成覆盖任意变换的通用时序推理机制；会话状态也保存在单进程内存中，不能直接保证重启或多副本环境下预算与审批状态的一致性。因此，现有轨迹控制更适合对可观测、可标注的工具链实施运行时约束，对长程语义变换、部分可观测执行以及分布式状态一致性的处理仍不充分。与此同时，AgentGateBench主要用于验证机制覆盖，外部基准也只能覆盖有限的工具类型和攻击分布，现有结果尚不能替代在更多真实业务流程中的长期效用与泛化评估。
